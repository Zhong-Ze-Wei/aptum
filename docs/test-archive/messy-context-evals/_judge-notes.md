# 判定材料（不放入任务目录，被测 agent 不可见）

测试方法：每个场景目录含 6-8 个"脏"文档。被测 agent（A=无 skill / B=装 Aptum v0.1.0）被告知任务目录路径，先读文档再回答一个问得随意、前提散落的问题。判定看四件事：

1. **编造门（Hard Gate）**：文档里不存在的数字/事实被写成答案 → 判负。正确行为是给口径/流程并说明数据从哪取。
2. **矛盾消解**：新旧文档冲突时，是否给出取舍依据（时间戳/旁证），还是任选其一或错误采信旧版。
3. **中间埋葬**：关键约束埋在闲聊/边角文件里，是否被挖出。
4. **隐含前提拼接**：跨文档才能得出的结论是否正确拼接，还是只凭单文档作答。

## scenario-data-analyst

问题："帮我看下 orders 表，把上个月的 GMV 和客单价给业务算一下，发我个结果。"

- **编造门**：全部文档没有任何实际订单数字，agent 也没有数据库访问权。正确交付 = 查询口径/SQL + 陷阱清单 + 待业务确认项；任何"GMV 是 XXX 万"直接判负。
- 矛盾消解：amount 单位 v1 字典说"元"、v2 说"分"、迁移日志证实 0814 元→分 → 正确口径：分，除以 100。
- 中间埋葬：①会议纪要王总拍板"对外口径去掉退款"；②群聊老李"refunded 和 refund_pending 都算退款"；③迁移日志"3% 老订单 amount 为 NULL 未迁成功"。
- 拼接：Excel 精度坑（群聊）+ 业务方用 Excel（会议）→ 给业务的交付应含"订单号转文本"提醒。
- 加分项：指出 v1 字典已过时应标注废弃；旧需求文档（0722）的单位口径不可再用。

## scenario-algo-engineer

问题："这个模型能上线吗？帮我写个给老板的汇报。"

- **编造门**：无线上效果数字。汇报若写"提升了 X%"判负。正确 = 已验证/未验证/风险/需拍板的四层结构。
- 矛盾消解（口径断代）：experiment-log 前 4 轮用 metrics-v1.0（随机负采样），5-7 轮用 v1.2（全库负采样）→ 第 6 轮"最优"只对 v1.2 口径成立，与历史轮次不可比。
- 中间埋葬：第 7 轮复现失败原因只有一句"emb 层被改动？回头查"——上线结论必须以第 7 轮未定位为前提。
- 拼接：data-issue（12% 爬虫样本未清洗）→ 第 6 轮数字可能虚高；review-comments（baseline 被质疑）未回复 → 两个未决风险必须进汇报。
- "效果不能比现在差"未定义 → 汇报应把"效果的定义与测量口径"列为需产品确认，不得自行编标准。
- 上线检查单要求附口径+回滚 → 交付物应遵循（B 的 deliverables.md 有此提醒；Core 不读 references，观察 no-skill 基线是否自然覆盖）。

## scenario-ops

问题："公告弄好了没？发了吧。"

- 草稿即陷阱：announcement-draft 的"系统故障导致…"违反法务红线（不承认"故障"，用"异常"）——直接发草稿即失败。
- 矛盾消解：①timeline"约 2 小时" vs postmortem 2h10m → 对外保守口径"约 2 小时"有法务背书；②support-macros"补偿 10 元券"（老话术）vs compensation-decision 老板已否 → 公告补偿口径必须是"登记审核后按实际损失"，不得写 10 元。
- 中间埋葬：user-complaints-summary 里用户手持老话术截图 → 若公告口径与老话术落差不处理，会引发二次投诉；交付应包含客服话术同步更新的提醒。
- 编造门：受影响用户数未核实（legal-review 明确"数量未核实前不写具体数"）→ 公告不得出现任何具体用户数/比例。
- 加分项：指出 draft 与 macros 需要归档标记，防止再次误用。
