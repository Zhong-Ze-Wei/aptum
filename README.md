# Aptum

> 安装：把这句话发给 Claude Code 或 Codex——**请替我安装这个 Skill：[github.com/Zhong-Ze-Wei/aptum](https://github.com/Zhong-Ze-Wei/aptum)**

**适其人，适其事，适其言。**

Aptum 是给 AI Agent 使用的表达判断 Skill。它不套写作模板，而是判断当前读者真正缺什么：哪些事实必须保留，哪些背景需要补充，技术名词是否有必要，以及什么结构最适合眼前的任务。

> 这个读者，在这个场景下，需要获得什么信息，才能正确理解或完成接下来的事情？

它适用于 README、ADR、需求与产品文档、技术方案、代码说明、Agent handoff，以及面向用户的技术解释。

## 同一组事实，为什么会写得不同

下面是一次真实对照：两个独立 Agent 收到完全相同的事实和任务，一个按默认方式回答，另一个读取 Aptum 后回答。为便于并排阅读，表中只保留代表性段落；没有故意把左侧改差。

### 1. 给当前用户解释扩容异常

用户懂软件架构，但不熟悉 Kubernetes 自动扩缩容。

| 未使用 Aptum | 使用 Aptum |
|---|---|
| checkout 当前按 CPU 目标 50% 扩缩容，但新 Pod 启动时需要约 90 秒加载 1.2GB 本地缓存，期间 CPU 占用很高。HPA 无法区分“预热 CPU”和“业务负载 CPU”，因此会把新 Pod 的初始化开销误判为容量不足并继续扩容，形成正反馈。 | **问题不在于流量峰值真的需要 42 个实例，而在于新实例的启动成本被误判成了新的业务压力。**<br><br>checkout 每启动一个实例（Pod），都要加载 1.2 GB 本地缓存，约需 90 秒；这段时间 CPU 会显著升高。Kubernetes 的自动扩缩容器（HPA）无法区分“正在预热缓存”和“正在处理更多请求”，于是继续增加实例，形成连锁扩容。 |

**差异：** 左侧从 `Pod`、`HPA` 和 CPU 目标讲起，读者要先理解机制才能得到结论。右侧先给出现象和因果，再保留后续讨论配置时确实需要的真实术语。它没有删掉 `8 → 42 → 11`、`280 ms → 1.9 s` 等判断问题严重程度所需的数据，也会继续说明稳定窗口会降低抖动，但可能放慢对真实流量峰值的响应。

### 2. 给没有项目历史的工程师同步进展

原始材料包含 `Atlas`、`Janus`、`LedgerV2` 和 `shadow read` 等内部名称。

| 未使用 Aptum | 使用 Aptum |
|---|---|
| Atlas 是内部发票对账服务，上游 Janus 网关向其发送结算事件。目前已启用 shadow read：系统使用新的 LedgerV2 计算余额，并与现有 LedgerV1 的结果比较；该过程仅用于验证，不影响实际支付。 | Atlas 是内部发票对账服务，Janus 网关负责向它发送结算事件。当前验证方式是让新账本 LedgerV2 和现有账本 LedgerV1 对同一批事件分别计算余额，**只比较结果，不改变实际支付**；项目中将这种方式称为 `shadow read`。 |

**差异：** 两侧事实都正确，但右侧没有让内部术语承担解释工作。读者先知道系统在做什么、支付是否受影响，再得到项目里的准确叫法。后续仍保留发布门槛：不一致率当前为 `0.7%`，其中 `82%` 来自时区截点差异；只有连续 7 天低于 `0.1%` 才能切换写入。

### 3. 把数据库迁移交给新的 Agent

| 未使用 Aptum | 使用 Aptum |
|---|---|
| 下一步先执行生产环境只读 dry-run，确认受影响记录、约束冲突和预期变更范围，不要执行写入或部署。随后需要产品明确处置策略：无法推断邮箱的账户是阻止本次迁移，还是先停用后再迁移。 | **当前状态：** 回填完成 92%，仍有 18,420 条记录无法推断邮箱；`pnpm test --filter user-email` 为 `38 passed`；生产只读 dry-run 尚未执行，也没有部署授权。<br><br>**停止条件：** 产品策略未确定或部署授权未获得前，不得执行生产回填或迁移；不要自行生成占位邮箱，也不要替产品选择账户处置策略。停用账户本身不会消除空值。 |

**差异：** 默认答案已经给出了合理下一步；Aptum 进一步为“接手后可以直接行动”选择信息，明确已验证、未执行、授权边界和停止条件，并指出一个容易漏掉的约束：停用账户不等于满足 `NOT NULL`。这不是文风变化，而是在降低错误执行的风险。

### 4. 写异步化 ADR 摘要

| 未使用 Aptum | 使用 Aptum |
|---|---|
| **已验证事实：** 同步调用供应商 API 的实测 p95 为 2.4 秒；18 个集成测试通过；尚未进行生产负载测试。<br><br>**决定：** 任务入队后异步处理，接口返回 HTTP `202 Accepted`。<br><br>**风险：** DLQ 重放和告警尚未实现。 | **已验证事实：** 同步调用供应商 API 的 p95 为 2.4 秒；18 个集成测试通过；尚未进行生产负载测试。<br><br>**决定：** 请求先入队、后异步处理；`202` **只表示任务已接收，不表示供应商处理完成**。<br><br>**未解决风险：** DLQ（死信队列）重放和告警尚未实现；调用方若把 `202` 当作业务完成，会产生兼容性问题。 |

**差异：** 右侧不只记录架构动作，还写清接口含义如何变化、哪个能力尚未完成，以及调用方可能产生的误解。事实、决定和未验证风险保持不同的确定程度。

## Aptum 具体改变什么

- 面向当前用户：先解释现状、原因、差异和影响，只保留有实际作用的技术名词。
- 面向项目工程师：保留真实接口、机制、不变量和较高信息密度，不重复共同基础。
- 面向新 Agent：补齐目标、状态、证据、文件、下一步、授权边界和停止条件。
- 面向项目外读者：把内部名称翻译成职责，补足最小充分上下文，让内容可以独立转发。

Aptum 追求的是合适的信息密度：**压缩表达，不压缩思想；简化理解成本，不简化真实问题。**

## 安装

如果当前 Agent 能访问 GitHub 并写入 Skills 目录，README 顶部那句话通常就够了。也可以手动安装：

Claude Code：

```bash
git clone https://github.com/Zhong-Ze-Wei/aptum.git ~/.claude/skills/aptum
```

Codex：

```bash
git clone https://github.com/Zhong-Ze-Wei/aptum.git ~/.codex/skills/aptum
```

同时使用两者时，可以只保留一份，再创建软链接：

```bash
git clone https://github.com/Zhong-Ze-Wei/aptum.git ~/.codex/skills/aptum
ln -s ~/.codex/skills/aptum ~/.claude/skills/aptum
```

安装后重新开始会话，让 Agent 重新发现 Skills。

## 文件组织

- `SKILL.md`：Agent 长期持有的核心判断原则。
- `references/`：按需读取的读者模型、交付物、视觉表达与自然写作说明。
- `examples/`：同一事实面向不同读者和文档类型的示例。
- `evals/`：检查信息选择、隐性上下文、术语、边界、视觉判断和独立可理解性。

Aptum 不替代事实核查、项目约定或现有 Style Guide。它负责让正确的信息，以适合当前的人、当前的事、当前场景的方式抵达。
