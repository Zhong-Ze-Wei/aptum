# Aptum

> 安装：把这句话发给 Claude Code 或 Codex——**请替我安装这个 Skill：[github.com/Zhong-Ze-Wei/aptum](https://github.com/Zhong-Ze-Wei/aptum)**

**适其人，适其事，适其言。**

Aptum 让 AI 学会真正意义上的“看人说话”：同一件事，对使用者、工程师、新加入项目的人或另一个 Agent，本来就不应该使用同一种表达。

从能力上说，Aptum 是一个面向 AI Agent 的表达判断 Skill。它让 AI 根据“谁在读、要做什么、在哪里读”，决定该说什么、说到什么程度、用什么方式表达。它不是一套写作模板，也不只是润色。

> **这个读者，在这个场景下，需要获得什么信息，才能正确理解或完成接下来的事情？**

只要 AI 正在把信息交给另一个人，Aptum 就可能有用：回答问题、解释复杂概念、项目汇报、需求与产品文档、技术方案、README、代码说明和 Agent handoff。

## 为什么需要它

一段话可以事实正确，却仍然没有帮助：给决策者讲了太多实现，给工程师省掉了关键边界，给新 Agent 只留下“继续处理”，给项目外的人留下了一串没人解释的内部名称。

Aptum 改变的不是固定文风，而是信息选择。同一份事实，读者和任务变了，真正需要出现的内容也会变。

## 三个真实场景

下面的事实来自作者的实际项目，表达经过压缩，但没有为了展示 Aptum 而虚构一个很差的对照答案。

### 1. 同一套系统，面对不同的人

[TencentDB Agent Memory](https://github.com/Tencent/TencentDB-Agent-Memory) 会把原始对话逐层整理成事实、场景和长期画像，并在需要时回到更具体的记录。面对不同读者，同一机制有不同重点：

| 面向产品使用者 | 面向项目维护者 |
|---|---|
| 它不会把所有历史聊天一次性塞给 Agent。系统先提供整理后的长期背景，让 Agent 快速进入状态；需要核对具体事实时，再回到更详细的记录。这样既减少重复解释，也避免旧信息挤满当前上下文。 | 记忆按 `L0 Conversation → L1 Atom → L2 Scenario → L3 Persona` 分层。组装上下文时以 L2/L3 做快速恢复，需要细节时通过 BM25、向量检索与 RRF 回到 L1/L0，并受条目数、字符预算和超时限制。 |

两边都没有更“高级”。使用者需要知道它解决什么问题，维护者需要知道真实层级、检索路径和容量边界。事实相同，信息密度不同——这是**适其人**。

### 2. 一句需求背后的隐藏知识

`learning-platform` 的目标看起来很简单：把 `ai-lab` 里的学习材料扫描到统一看板。

| 只看字面需求 | 补出执行所需的上下文 |
|---|---|
| 遍历 `learn-*/docs/**/*.md`，读取文档并展示。 | 项目里的材料没有统一目录：`learn-e2b` 只有 `README.md`，`web_search_test` 的文档在模块根目录，`learn-pi` 才使用 `docs/*.md`；`pi/pi` 还是不能算作个人学习产出的上游参考源码。因此不能从目录名猜规则，每个主题需要显式声明 `docs_include`，扫描器只读取这份范围。 |

这里缺的不是一句更漂亮的需求，而是作者知道、实现者却不知道的项目结构。Aptum 会寻找足以改变方案的隐性上下文，不会假装规则已经存在——这是**适其事**。

### 3. 汇报给人，还是交给 Agent

`TencentDB-Agent-Memory` 有一个发布三个 Docker 镜像的脚本。给人同步进展和交给 Agent 执行，所需信息完全不同：

| 项目进展 | Agent handoff |
|---|---|
| 三个公开镜像的发布脚本已经具备统一发布、单组件发布、dry-run 和本地构建能力。 | **入口：** `deploy/dockerhub/publish.sh`。<br><br>**约束：** `VERSION` 必填且不能以 `dev-` 开头；默认 `PUSH=1` 会真的推送镜像。`DRY_RUN=1` 只做敏感信息扫描和构建目录准备，不会构建；`PUSH=0` 才是本地单架构构建并抽查镜像。<br><br>**边界：** 仓库说明了脚本能力，没有提供本次发布授权；未得到明确授权时不要使用默认推送模式。 |

对另一个 Agent 来说，“接下来运行脚本”还不够。它必须知道入口、真实行为、已知约束和哪里不能继续。表达形式需要为安全执行服务——这是**适其言、适其场景**。

## Aptum 到底改变什么

- 保留会改变理解、决定或行动的事实，减少没有信息增量的内容。
- 补足读者不知道、但作者容易默认存在的最小上下文。
- 根据读者决定术语、解释深度和信息密度，不把“简单”当成唯一目标。
- 区分已验证事实、推断和建议，保留边界、风险与停止条件。
- 当流程、状态或结构用图表更清楚时选择图表；简单内容不机械画图。

> **压缩表达，不压缩思想。**\
> **简化理解成本，不简化真实问题。**

Aptum 没有固定文风。面向管理者可能更短，面向工程师可能更技术化，面向新人需要补背景，面向 Agent 则需要明确状态、证据和停止条件。

## 安装

如果当前 Agent 能访问 GitHub 并写入 Skills 目录，README 顶部那句话通常就够了。也可以手动安装：

```bash
# Claude Code
git clone https://github.com/Zhong-Ze-Wei/aptum.git ~/.claude/skills/aptum

# Codex
git clone https://github.com/Zhong-Ze-Wei/aptum.git ~/.codex/skills/aptum
```

安装后重新开始会话，让 Agent 重新发现 Skills。

## 使用

告诉 Agent 内容要交给谁，以及读者需要完成什么：

```text
使用 Aptum，把这份项目进展改成业务负责人能够据此决定是否上线的说明。
```

```text
使用 Aptum，把当前工作写成新 Agent 可以安全继续、但不能自行部署的 handoff。
```

Aptum 不替代事实核查、项目约定或现有 Style Guide。它负责让正确的信息，以适合当前的人、当前的事、当前场景的方式抵达。
