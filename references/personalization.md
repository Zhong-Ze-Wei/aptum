# 长期读者模型

长期读者模型只保存为了让当前用户正确理解和行动而稳定有用的信息。它回答“怎样把信息交给这个人”，不回答“这个人是什么样的人”。

## 作用范围

当前明确要求、适用的项目约定和当前会话证据优先。长期模型只提供先验；它不能覆盖当前受众、交付目的、事实、权限或格式要求。一个领域的知识判断不能自动迁移到其他领域。

模型只在主要读者是当前用户本人时适用。写给经理、客户、项目新人或另一个 Agent 时，以真实接收者为准，不把本次适配写回长期模型。

没有长期模型时正常完成任务。不要中断首次使用要求初始化，也不要仅为创建画像而追问。

## 可以保存什么

只保存能稳定改变信息选择、解释深度、术语或结构的规则：

- **Knowledge**：有明确领域范围的已知知识和待解释边界；
- **Preference**：信息密度、解释顺序、术语和结构偏好；
- **Correction**：用户希望 Agent 主动抵消的表达惯性，写成可执行规则。

Correction 应描述输出行为，例如“结论与关键原因已经闭环时停止”，不要写成“用户容易过度解释”等人格判断。

不保存年龄、性格、价值观、笼统职业标签、敏感个人信息、偶发受众、临时角色、单个项目状态或一次性的格式要求。某条信息不能改变 Aptum 的表达判断，就不应进入模型。

## 建立与维护

识别可以自动，持久化不能静默：

- 用户明确要求“以后这样”或“记住这个偏好”时，可以保存清楚、稳定且范围明确的规则；
- 用户要求根据交流建立模型时，先生成草稿，区分明确事实与推断，得到确认后再保存；
- 仅从行为推断出的候选在当前会话内使用。只有它反复造成明显返工时才值得询问一次，未确认就丢弃；
- 新规则与旧规则冲突时修改或替换旧条目，不并列保存矛盾偏好；
- 用户可以要求查看、修改或删除任意条目。删除后不从历史对话自行恢复。

只保存已确认的当前规则，不维护 `candidate`、置信度、出现次数或变更日记。优先合并重叠内容，让模型保持可扫描；通常不需要超过十几条。

## 本地存储

本地文件系统可用时，默认读写：

```text
~/.config/aptum/reader-profile.md
```

不要把个人读者模型写入 Aptum 仓库、公共 reference、README 或随 Skill 发布。若宿主已经提供用户确认的稳定偏好，可以直接使用；多个长期来源冲突时，以用户当前明确确认的内容为准，无法判断且会显著影响交付时再询问。

推荐使用可直接编辑的 Markdown：

```markdown
# Aptum Reader Profile

当前任务、项目约定和当前会话始终优先。

## Knowledge

- [AI / Agent] 可以直接使用 Agent、Prompt 和 Skill 等概念。
- [基础设施] 不默认熟悉具体运行机制；相关时简短解释。

## Preference

- 默认先给核心判断，再解释最关键的原因。
- 保留必要的真实术语；陌生或易误解的术语首次出现时解释。

## Correction

- 结论和关键原因已经形成信息闭环后停止，等待追问。
```
