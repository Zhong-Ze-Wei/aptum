# 读者模型

这里不是四套固定语气模板。它提供的是信息选择差异。先识别读者要完成的事，再使用最接近的模型；真实受众可以跨类别。

## 当前用户本人

根据当前对话、用户明确表达的背景和可用的稳定偏好判断其知识边界，不默认其是初学者或专家。一次任务中的角色和受众不属于长期用户身份。

优先回答：

- 现在是什么状态，已经确认了什么；
- 与此前或常见做法相比发生了什么变化；
- 产生这个结果的原因或机制；
- 哪个约束真正改变决策；
- 方案的收益、代价、边界与后续影响；
- 哪些地方容易被一个合理但错误的 mental model 误解。

直接使用用户已经掌握的基础概念。新术语第一次出现时解释它在当前问题中的作用，不展开通识课程。对于代码或系统问题，最好把抽象结论落到真实组件、状态或例子上。

不要把输入里出现的每个技术名词都原样转交。先说明用户能观察到的现象、因果和影响；只有读者接下来需要讨论配置、查找实现或区分相近机制时，再给出真实名称。普通语言应替换无用标签，不能替换数字、条件和边界。

## 学习与教学场景

“学习者”是当前任务中的状态，不是长期身份。先判断读者要学会什么、已经拥有什么 mental model，以及当前缺少的最小理解环节。

先建立足以支持下一步的因果、结构或辨别方法，再引入真实术语和必要边界。示例用于暴露机制或常见误解，不用于装饰。不要机械要求类比、逐步教学、练习题或结尾总结；表达形式由学习目标、读者已有知识和交付媒介决定。

## AI Agent

Agent 的主要风险不是“看不懂术语”，而是缺失状态后重新猜测、重复劳动或越过边界。表达应支持继续执行和失败恢复：

- 目标与完成定义；
- 当前状态，已完成、未完成和未验证的内容；
- 相关文件、符号、命令、输入输出和证据位置；
- 已做决策、理由、不变量、授权边界和禁止事项；
- 已尝试路径及其结果，尤其是不可重复或有副作用的动作；
- 下一步和停止条件；
- 推断、建议与已验证事实的区别。

上下文完整不等于原样倾倒日志。保留能改变下一步的信息，用标题、短列表、表格或状态块让 Agent 快速定位。不得把凭据、个人数据或无必要的大段敏感输出塞入 handoff。

## 项目内工程师

这类读者通常知道产品、代码库和团队术语，但未必知道当前改动。使用高信息密度和真实名称：

- 先讲行为或接口发生了什么变化；
- 指出受影响的模块、数据流、调用关系和不变量；
- 说明为什么采用该方案，以及放弃方案的实际代价；
- 写明兼容性、迁移、并发、故障、观测和回滚边界；
- 提供足够证据让对方复核，不重复语言或框架常识。

“大家都知道”只适用于稳定的项目共识。跨团队缩写、历史事故和非显然约束仍应补一句。

## 没有历史上下文的人

把读者看作聪明的新加入者，不看作初学者。优先补齐作者最容易忽略的四种上下文：

1. **对象**：这个系统、模块或决策负责什么，不负责什么。
2. **起因**：当前问题为何存在，旧行为造成了什么具体后果。
3. **约束**：哪些条件不能随意改变，原因是什么。
4. **位置**：本结论处于哪一阶段，哪些内容已落地，哪些仍是提议。

上下文补到足以解释当前判断。除非历史本身影响决策，不按时间线复述项目全部沿革。

项目代号、组件名和内部流程名不能充当背景说明。首次出现时把名称与职责放在一起，如 `Atlas`（负责发票对账的内部服务）；若名称对理解和后续行动都没有作用，直接写职责。通用表达的目标是让内容可转发，不是把真实约束概括成空泛结论。

## 混合受众

README、RFC、ADR 和技术方案经常同时服务人和 Agent，也会被搜索或片段检索。可以采用分层结构：

- 开头给出目标、当前行为和适用边界；
- 正文保留真实术语、机制和决策依据；
- 用一句局部定义照顾非专家；
- 将完整 API、命令或历史证据放到清晰命名的章节；
- 让每个关键章节在脱离前文被检索时仍知道主语和适用条件。

不要为照顾混合受众把每句话写成折中语气。让不同层次各自可定位。
