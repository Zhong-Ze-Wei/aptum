# 交付物高风险遗漏提醒

这不是文档写法指南——README 一般要介绍项目、ADR 要有背景和决定、PR 要说改动，这些模型已经掌握。本文件只提醒**不明显、但遗漏后会改变下游行动**的点。交付物本身没有这类信息需求时，不需要读本文件。

## ADR

- 触发复审的条件如果重要，不能丢（"若业务要求请求内确认送达，应重新评审本决定"）——它是未来读者判断"决定是否仍成立"的依据；
- 不要事后把当时的不确定性改写成必然，不列从未认真考虑过的陪跑方案。

## Release note / 版本更新说明

- Breaking change 对**现有用户**的迁移动作置顶（依赖版本门槛、废弃接口的替代路径、截止时间），不能埋在功能列表末尾；
- 用户视角的判断信息："我受影响吗、我要做什么、不做会怎样"。

## Agent handoff / 交接

- 停止条件和授权边界必须显式（"产品未确认前不得继续生产迁移""没有发布授权"）；
- 已验证与未验证的区分不能在压缩中消失；
- 见 SKILL.md 交接不变量清单——本文件只补充：失败尝试和不能重复的副作用也要保留。

## API / 接口文档

- 素材未提供的 schema、响应字段、错误码**不得补造**；需要示例时标注"按通用约定，以实际为准"或"字段名待接口确认"；
- 边界值（上限、默认、窗口）显式写出，不概括成"有长度限制"。

## 评审与决策材料

- 真正需要拍板的问题要暴露出来（选项、代价、建议），不能只呈现已完成分析让决策者以为一切顺利；
- 技术债、排期类材料的判断依据是影响和代价（谁在投诉、阻塞什么、修复成本），不是问题描述本身。

## 需求 / 产品文档

- 尚未确定、需要业务选择的事项显式列出，不假装规则已存在；
- 非目标与边界条件（重放是否绕过去重、收据是否在范围内）会改变验收，不能省略。
