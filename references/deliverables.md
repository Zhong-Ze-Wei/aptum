# 常见交付物的表达判断

这些不是必须照抄的模板。每一节指出该交付物帮助读者完成什么，以及哪些信息最容易漏掉。项目已有结构和 house style 优先。

## README

README 帮助第一次接触仓库的人判断“它是什么、是否与我有关、怎样开始、哪里会踩坑”。通常需要：

- 一两句说明项目解决的问题和边界，而不是口号；
- 当前可用状态、关键前提和最短成功路径；
- 可验证的命令与预期结果；
- 配置、架构或目录关系只写到支持首次使用和继续探索的程度；
- 已知限制、兼容范围和下一步文档入口。

对主要模块或请求流的概要，如果一张图比目录列表更直观，就使用图。不要把 README 变成完整 API reference 或项目编年史。

## ADR

ADR 让未来读者理解“为什么当时这样决定”，而不只是记录最终方案。保留：

- 决策状态和日期；
- 当时的上下文、问题和不可变约束；
- 被采用的决定；
- 真正参与权衡的备选方案；
- 可预期后果，包括收益、成本、风险和触发复审的条件；
- 事实、当时推断与团队选择的区分。

不要事后把不确定性改写成必然，也不要列出从未认真考虑过的“陪跑方案”。

## 需求或产品文档

这类文档首先约束“谁遇到什么问题，系统必须表现成什么样”，而不是提前锁死实现：

- 用户、触发场景和现有痛点；
- 目标结果与明确非目标；
- 可观察行为、状态变化和异常路径；
- 业务规则、权限、数据保留与兼容边界；
- 可验证的验收标准；
- 尚未确定、需要业务选择的事项。

只有当实现约束会改变产品行为、成本或可行性时，才把它带入主叙述。状态机、角色权限矩阵和前后体验流程通常比连续文字更清楚。

## 技术方案、RFC 或架构说明

目标是让工程师能够评审正确性、代价和落地路径：

- 当前系统与具体问题；
- 目标、非目标、约束和成功条件；
- 拟议结构、组件责任、接口、数据和状态流；
- 关键不变量与失败处理；
- 备选方案和选择理由；
- 迁移、兼容、观测、回滚、安全和容量影响；
- 未决问题与验证计划。

图用于说明拓扑、边界、顺序和状态；正文负责解释为什么、例外和权衡。不要让组件框图代替接口约束，也不要用大段伪代码隐藏仍未决定的设计。

## Agent handoff

handoff 的完成标准是另一个 Agent 不依赖原 conversation 就能安全继续：

- 任务目标与完成条件；
- 当前工作树或环境状态；
- 已完成修改及其位置；
- 验证过的事实、执行过的测试和结果；
- 做过的决定及理由；
- 失败尝试和不能重复的副作用；
- 剩余工作、建议顺序、风险与停止条件。

写真实路径、符号、命令和状态。不要只写“基本完成”“继续优化”或粘贴整段聊天记录。

## 代码相关说明

代码说明可能在回答不同问题，先分清读者要哪一种：

- **它做什么**：输入、输出、副作用和调用位置。
- **它怎样工作**：关键控制流、数据结构、状态与错误路径。
- **为什么这样写**：约束、历史原因、替代方案和不变量。
- **改动影响什么**：行为差异、兼容性、风险和验证范围。
- **怎样修改**：安全入口、相关测试和常见破坏方式。

引用真实文件、符号和最小必要代码片段。不要逐行翻译显然代码；把注意力放在代码本身无法直接说明的关系和理由上。若行为未经运行或测试验证，明确说是静态阅读所得的推断。

## Issue、PR 和开发计划

这些文本是协作接口。读者需要快速判断问题、范围、影响和下一步：

- Issue 写清复现条件、实际与预期行为、证据、影响和已排除因素。
- PR 先说明外部行为变化，再说明实现和验证；风险、迁移或待跟进事项不可藏在 diff 中。
- 开发计划按依赖和可验证结果组织，不按“分析、开发、测试”这类空阶段拆分。

使用列表帮助扫描，但有因果关系的内容保留为连贯文字。
